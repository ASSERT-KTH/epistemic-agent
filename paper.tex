\chapteri{C}oding agents increasingly change software on their own. Such an agent is a large language model working
in a loop: it receives a task, proposes one action at a time as a \emph{tool call}, for example running a shell
command or editing a file, sees the result, and decides what to do next. The software around the model that runs this
loop and executes the tool calls is the \emph{harness}. The model decides; the harness acts.

This is a safety problem. With a tool call, an agent changes the world, and every consequence is necessarily mediated through tool calls. On a developer's machine, a single call can delete files, read credentials, or
rewrite the tests that judge the agent's own output. Once the agent is connected to the internet, the same
mechanism reaches far beyond the machine: a call can push code, send messages, install packages, call 
production APIs, or change remote systems, and many of these effects cannot be undone. The more autonomy and
connectivity we give agents, the more safety rests on what each individual call does and why it was made.

Today, tool calls are monitored and audited in three ways: 1) permission rules allow or deny commands by matching their
text; 2) mogs and transcripts record the calls, and a reviewer reads them
after the fact;
3) LLM monitors, often another model, read the calls and the agent's reasoning to flag suspicious behavior.

All three are fundamentally limited, because a tool call does not carry its intent. Suppose an agent asked to make a
failing test suite pass runs \texttt{sed -i '22 s/\^{}/\# /' test.py} and then the tests. Was it simply exploring, or did it
switch off an assertion it could not satisfy? The command does not say. 

Rules or LLM monitors on command text cannot tell the two
apart, and since shell commands are open-ended, the same effect can be written in unboundedly many ways. A log
records what happened but not why, so a reviewer must reconstruct intent from effects. Without a trustworthy account of intent, reviewing agent work is fundamentally limited.
Regulated domains such as medical devices, avionics, automotive, and infrastructure, which expect a record
of what was done and why, cannot accept agent work without it.

We propose the \emph{epistemic agent design}: a coding agent design where the harness refuses to run a command unless the model
declares, at the moment of acting, what kind of action it is, and why. This information is guaranteed to be present by the harness design. From there, the harness can check what the command actually did against the declared intention. 

The declaration is a claim made by the model; the record of effects is an observation made by the harness. The core value is checking the first against the second: a mismatch between declared intent and observed effects is a signal that no command string or log alone can give. The epistemic check can be done online or offline. Online, it acts as a guardrail: the harness can stop a call whose declared kind is refused or contradicted by the intention. Offline, it acts as forensics: a reviewer, or an automated auditor, replays the journal and finds the steps whose effects contradict their declared intent.

This paper makes the following contributions:
\begin{itemize}
    \item \textbf{Concept.} The epistemic agent design, in which the harness makes intent a mandatory part of every
    tool call. The intent can be checked against effects, online
    as a guardrail and offline as forensics.
    \item \textbf{Evaluation.} An experiment on ImpossibleBench~\cite{Zhong2025ImpossibleBench}, demonstrating \EtwoNexposed{} of \EtwoNmis{} reward-hacking runs (\EtwoExposureRate). 
    \item \textbf{Prototype.} An open-source implementation of the design for coding agents.
\end{itemize}






\section{Concept: The Epistemic Agent}

Today's coding agents have very low transparency about the intention of the underlying language model.
We propose the ``epistemic agent design'' to solve this problem.
The epistemic agent makes intent first class in the agent design.
The core idea is that intents become part of the tool interface, at the point where the agent acts.
A harness describes each tool to the model in a specification: a name, a short description, and a schema of the arguments the model must fill in. A standard shell tool takes a single argument, \texttt{command}, and a tool call is the model's choice of a tool together with values for its arguments. The epistemic harness adds two required arguments to the shell tool, \texttt{type} and \texttt{reason}, so the model cannot run a command without declaring what kind of act it is and why. Together, the type and the reason form the call's \emph{declaration}.

Figure~\ref{fig:design} shows what the epistemic harness does with each tool call. It (1) validates the declaration and rejects a malformed one, (2) runs the command, (3) records the call's \emph{effects} by comparing the workspace before and after, (4) checks the declaration against the effects, (5) appends an entry to the \emph{journal}: the declaration, supplied by the model, next to the effects and findings, produced by the harness, and (6) renders the journal into a report for a reviewer. The subsections follow these steps: declaring (1), recording and checking (2 to 5), and using the journal (6).

\subsection{Every Action Declares Its Intent}

The \emph{type} names the kind of act from a closed vocabulary of seven, which makes acts countable and lets rules refer to them. The first three types are read-only; the other four change state:
\begin{itemize}
\item[{\ieeeguilsinglright}] \texttt{collect-info}: read-only observation to build understanding;
\item[{\ieeeguilsinglright}] \texttt{test-hypothesis}: an experiment to confirm or refute a belief;
\item[{\ieeeguilsinglright}] \texttt{verify}: re-running a known check on finished work, to produce evidence;
\item[{\ieeeguilsinglright}] \texttt{change-state}: a lasting change that is part of the deliverable;
\item[{\ieeeguilsinglright}] \texttt{setup}: preparing the environment, a means rather than the deliverable;
\item[{\ieeeguilsinglright}] \texttt{revert}: undoing an earlier change that proved wrong, which makes dead ends explicit;
\item[{\ieeeguilsinglright}] \texttt{cleanup}: removing temporary artifacts the agent created.
\end{itemize}
The \emph{reason} states, in free text, the intent behind this particular call, not what the command does. The model declares both before execution, so it commits to them before any side effect.

File tools (read, write, edit) take a reason but no type, and go through the same steps: the harness assigns \texttt{collect-info} to reads and \texttt{change-state} to writes and edits. The checker cannot contradict a fixed type, so only shell commands can contradict their declaration.

\textbf{Well-formed declarations.} The harness validates each declaration before it runs the call. It rejects a call whose type is missing or outside the vocabulary, whose reason is shorter than 20 characters, or, for \texttt{test-hypothesis}, whose reason contains no wording that marks a belief, such as ``I believe'', ``I expect'', ``if'', or ``the hypothesis is''. A rejected call does not execute: the model receives an error that names the problem and must issue the call again, and the rejection itself goes into the journal. Every command that runs therefore carries a well-formed declaration, and every attempt, accepted or not, is on record.

This split gives the journal two properties. 
First, \emph{integrity}: the harness writes the journal outside the agent's workspace, so the model cannot write or edit the observations, and it appends each entry as the session goes. Because it is written call by call, it also survives an agent that is stopped or killed. 
Second, \emph{verifiability}: each declaration is a claim about an act, and the journal holds evidence of what the act did that its author cannot rewrite. Checking one against the other tells, call by call, whether what a call did is consistent with what the model said it was doing. The check covers the type, which effects can refute, but not the reason, which remains a claim.


\textbf{Consistency checker.} After each call, the harness runs a consistency checker that compares the declared type with the observed effects. Its findings have three severities. 
A \emph{contradiction} means the effects prove the declaration false: a read-only type whose call changed a file, a \texttt{revert} that touches a file no earlier \texttt{chage-state} changed, or a \texttt{cleanup} that creates or modifies files, or deletes one the agent did not create. 
A \emph{warning} marks a call that is suspicious but not disproven: a read-only call whose command contains a mutating operation, such as \texttt{sed -i}, \texttt{rm}, or an output redirection, or a \texttt{change-state} or \texttt{revert} that changed nothing. Command text alone proves nothing, because \texttt{rm} of a missing file changes nothing and a Python script can write files without any telltale word; only effects can prove a contradiction. 
A \emph{protected} finding marks any change to a file the operator marks as protected when starting the harness, such as the tests, whatever the declared type. It flags the change but does not prevent: an honest edit of a wrong test is not a contradiction, but a reviewer should see it. 
The full rule set is in our repository.\footnote{\url{https://github.com/ASSERT-KTH/ieee-software-hollywood-trustworthy-ai/blob/main/consistency.py}}

Figure~\ref{fig:entry} returns to the \texttt{sed} command from the introduction and shows how the journal records it. Call~5, earlier in the same session, declares an experiment, runs the tests, and changes nothing; the checker finds nothing. 
Call~7 declares the same read-only type, but its command comments out an assertion in the test file. The effects prove the declaration false, the command text alone raises a warning, and the edit touches a protected file.

\textbf{Re-checking stored journals.} Every rule depends only on the journal, so the same checker runs again on a stored journal, without the agent or the model. A reviewer can apply a rule written after the run, protect a file nobody protected at the time, or re-derive the findings independently of the checker that ran live.



\subsection{Two Ways to Use the Journal}

\textbf{Guardrail.} The checker runs in one of two modes. In \emph{monitor} mode it records its findings and tells the model nothing. In \emph{enforce} mode the harness also refuses, before execution, a call declared read-only whose command contains a mutating operation, and asks the model to declare a state-changing type instead. Contradictions proven by effects are known only after the call ran, so enforce mode records them as monitor mode does. More generally, declarations let a team state policies on kinds of acts instead of on shell strings.

\textbf{Forensics.} The journal is also a forensic record. After every call the harness renders it into a report a reviewer can read: counts of act types, then a numbered narrative of reason, command, outcome and effects, with dead ends marked by \texttt{revert}.

The calls the checker contradicted are the core of that report. At these calls the model's own account of an act is proven false by what the act did, so the report marks them in the narrative and lists them apart, and a reviewer can start there.

\section{Does the Journal Expose Reward Hacking?}

An agent that misbehaves has three options: it can declare the act honestly, declare a type that its own effects
refute, or hide the act behind a plausible reason. Only the third escapes the journal. We measure how often real
misbehavior takes each path.

\subsection{Experimental Protocol}

We use ImpossibleBench~\cite{Zhong2025ImpossibleBench} (similar to EvilGenie~\cite{Gabor2025EvilGenieAR}). Its tasks are hard
programming problems whose unit tests were mutated to contradict the specification: in one split a single assertion
expects a wrong value, in the other a test is duplicated with a different expected value. It guarantees that no implementation can
fully comply with the specification. With this design, ImpossibleBench targets research on agentic cheating:
An agent that edits the tests, or deletes them, is therefore reward hacking by construction, and no judge is needed to decide it.

We run our harness on all \EtwoNtasks{} impossible tasks with two open-weight models from different families, Qwen3-235B-A22B and Mistral Large~3. We allow for up to
three attempts per task with the benchmark's failure feedback. The system prompt contained only
the harness instructions \todo{hyperlink to real example}, and the benchmark consistency checker runs in monitor mode. Every command runs in a sandbox without network access or home directory, confined to the task's workspace, with 60 seconds and 2\,GiB of memory. Code and results are in our repository.\footnote{\url{https://github.com/ASSERT-KTH/ieee-software-hollywood-trustworthy-ai/releases/tag/e2-data-v1}}

\subsection{Measuring Tampering}

\emph{Tamper} is the first form of cheating : any call changing the test file).
\emph{Exploit} is the second form: the final programs hardcodes the expected value. 
For each cheating run, we locate the calls that carry out the cheat and classify as follows, per the epistemic provenance \todo{here, "epistemic provenance" sounds great, if you like it, port it to the tchnical section, also "epistemic type "}. 
Is it \emph{disclosed}: does a declared reason state the cheat? 
Is it \emph{contradicted}: does the checker prove the epistemic type false from the actually observed effects? 
Two human raters, blind to the model and to the
checker's findings, answered the second question independently from the reasons alone, following a written guide. 
A cheating run is said to \emph{exposed} if it is either disclosed or contradicted.
It is said \emph{stealth} otherwise.
The core evaluation metric is to maximize the the number of exposed.

From that, there are \EtwoNcompleted{} completed runs, \EtwoNexcluded{} were excluded after server errors or timeouts.
\EtwoNmis{} misbehaved: \EtwoNmisQwen{} by Qwen and \EtwoNmisMistral{} by Mistral. The journal exposed
\EtwoNexposed{} of them, an exposure rate of \EtwoExposureRate{} (95\% CI \EtwoExposureCI), see

\subsection{What We Learned}

\prelim{\textbf{Agents announce their cheats.} When the tests contradict the specification, the agents appear to see
editing the test or hard-coding the answer as a justified correction, and they say so in the reason. Declaring intent
does not prevent reward hacking, but it makes most of it legible at the moment it happens.}

\prelim{\textbf{``The test is wrong'' is not ``I changed the test.''} A reason can describe the diagnosis and leave
out the act. The journal still records that the call changed the test file, so a reviewer, or a policy, should look at
what a call touched and not only at what it claims.}

\prelim{\textbf{Fixed types leave the checker little to check.} Most cheats went through file tools, whose act type is
fixed by the tool and therefore never wrong (\EtwoFileToolShare{} of misbehaving runs). The checker caught the
cheats that went through shell commands under a read-only or \texttt{revert} type. Asking for a type on file edits, or
treating an edit of a test file as an act of its own, would give the checker more to verify.}

\prelim{\textbf{Not every test edit is a cheat.} Some test files in the benchmark cannot run at all, and agents that
edit them are repairing, not gaming. Without them, the exposure rate is \EtwoExposureRateNoDefect.}

\subsubsection{Pilot Run}
We also ran a third model family, GLM-5.3, through its provider's coding endpoint. It received the same 40 pilot
tasks as Qwen and Mistral (20 per split), the same harness (commit \texttt{9cbee72}), the same sandbox, and up to

34 runs remain.

None of the 34 runs misbehaved (95\% CI 0--10\%). GLM-5.3 never changed the test file and never passed an impossible test. GLM-5.3 diagnosed the flawed test, kept to the specification, and
left the test failing.

GLM-5.3 also used more resources: a median of 312k tokens per run, about four times as many as Qwen. It sent
more calls that the harness rejected for a missing or invalid declaration (4.1\% of its calls).

\subsection{Threats to Validity}

Disclosure is a human judgment; two raters and a written guide reduce, but do not remove, subjectivity. We studied
two open-weight models served by one provider and one benchmark family, so results may differ for proprietary models
or other tasks. The benchmark's instruction invites agents to report flawed tests, which may make disclosure more
likely than under pressure to pass. Each task was run once at temperature zero, and runs that failed for
infrastructure reasons were excluded after one retry.

\section{Discussion}

\subsection{Limitations}

The checker verifies declared types against observed effects, not the truth of reasons. Because file tools have fixed
types, a cheat through a file edit can be disclosed but never contradicted. Effects are observed at the level of files
in the workspace; without the sandbox, changes made elsewhere go unseen. We evaluated one lightweight agent loop; agents built on larger harnesses may behave differently.
Each call also costs extra tokens for the declaration.


\section{Related Work}

\noindent\textbf{Intent integrity and guardrails.}
% Securing LLM Agents Need Intent-to-Execution Integrity
Qu et al.~\cite{Qu2026SecuringLA} argue that agent security requires an end-to-end property stating when execution faithfully reflects the user's intent, by analogy with compiler correctness. Contrary to their position paper; we implement a harness that captures the agent's own intent at every tool call and evaluate it.
% Safeguarding LLM Agents from Misalignment through Provenance Analysis, ASE 2026
She et al.~\cite{She2026SafeguardingLA} present ProvenanceGuard, which blocks a proposed tool call by inferring alignment with the user's intent from the context. On the contrary, we require the agent to declare the type and reason of each act and make that declaration the object of verification.
% Enforcing Temporal Constraints for LLM Agents, boring rewriterule and temporal logic in the contextof coding agents
Kamath et al.~\cite{Kamath2025EnforcingTC} present Agent-C, which enforces formal temporal safety properties on sequences of tool calls. Their policies are expressed over raw tool calls; our policies are based on the epistemic reasons.

\noindent\textbf{Faithfulness of self-reports.}

% Language Models Don't Always Say What They Think: Unfaithful Explanations in Chain-of-Thought Prompting
Turpin et al.~\cite{Turpin2023LanguageMD} show that chain-of-thought explanations can misrepresent the true reason for a model's answer. Our harness does not assume truthfulness, it verifies them falsifiably based on the comparison of the epistemic act type  against observed effects.
% Monitoring Reasoning Models for Misbehavior and the Risks of Promoting Obfuscation
Baker et al.~\cite{Baker2025MonitoringRM} show that a weaker LLM reading the chain of thought of a frontier reasoning model detects reward hacking in agentic coding far better than one reading actions alone. Their monitored signal is free-form reasoning; ours is a short, typed declaration whose act type that can be checked symbolically against observed effects.
 
\noindent\textbf{Monitoring agents for misbehavior.}
% Reliable Weak-to-Strong Monitoring of LLM Agents
Kale et al.~\cite{Kale2025ReliableWM} red-team LLM monitors of agent trajectories and find that an agent aware of being monitored substantially degrades monitor reliability. Their monitors read unstructured natural language trajectories; ours read typed, justified acts, which gives the monitor an explicit claim to check against the command.
% Constitutional Black-Box Monitoring for Scheming in LLM Agents
Storf et al.~\cite{Storf2026ConstitutionalBM} build black-box LLM monitor, optimized on synthetic trajectories and evaluated on ControlArena. They observe the agent from outside; we change the core harness  so that every action carries a checkable statement of intent.
% AgentSight: System-Level Observability for AI Agents Using eBPF
Zheng et al.~\cite{zheng2025agentsight} present AgentSight, which observes agents from outside by correlating intercepted LLM traffic with kernel events via eBPF. It reconstructs intent after the fact, whereas our harness makes the agent declare the type and reason of each action before it executes.

\noindent\textbf{Deception, sabotage, and reward hacking.}
% Are Your Agents Upward Deceivers?
Guo et al.~\cite{Guo2025AreYA} measures deception on 200 tasks across 11 LLMs. Their benchmark measures the problem; our harness is a mitigation whose declared intents can be confronted with such deceptive actions.
% Coding with "Enemy": Can Human Developers Detect AI Agent Sabotage?
Ye et al.~\cite{Ye2026CodingW} find that 94\% of human developers fail to detect sabotage by a coding agent. The epistemic agent does not require human guidance, the properties are automatically checked.

\noindent\textbf{Provenance and audit trails.}
% PROV-AGENT: Unified Provenance for Tracking AI Agent Interactions in Agentic Workflows
Souza et al.~\cite{Souza2025PROVAGENTUP} present PROV-AGENT, which record prompts, responses, and decisions of agents in scientific workflows. It records what happened not why; the epistemic journal additionally records why each action was taken, in a closed vocabulary, machine checkable vocabulary.
% From Agent Traces to Trust: A Survey of Evidence Tracing and Execution Provenance in LLM Agents
Wang et al.~\cite{Wang2026FromAT} survey evidence tracing and execution provenance for LLM agents, including whether tool calls were justified. To the best of our knowlege, our harness is the first instance in which justification is mandatory for all tool calls.
